# GPT-6 Luna high：SMM 充分性判断小样本试跑

此试跑只回答“Luna high 能否按冻结输入正常输出、输出是什么样”。它不是 257 题实验的准确率结果，也没有执行第二轮补查。

## 输入和调用

- 预先固定 `P01, C037, L011, P07` 四题，顺序见 `protocol.json`；保留 SF001 首轮的完整对话、时间、提示和 JSON schema，只把模型名从 `gpt-6.1-sol` 改成 `gpt-6-luna`，思考档位仍为 `high`。
- 使用既有 Codex 订阅 `app-server` 传输，实际回执校验模型为 `gpt-6-luna`、服务商为 OpenAI、工具调用为零。
- 单线程，每次请求开始至少间隔 45 秒；无应用层重试。每题请求、原请求哈希、完整输出、引用校验、用时和 token 数保存在本目录。
- Sol 对照来自同题 SF001 首次记录；两模型输出未互相喂给对方。

| 题目 | 首轮依赖证据 | Luna high | Sol high | 本次观察 |
| --- | --- | --- | --- | --- |
| P01 《夜莺》读完了吗 | 齐 | 充分 | 充分 | 两者都找出较新的明确完成记录。 |
| C037 Sam 和 Evan 的健康惊险经历 | 缺 | 充分 | 充分 | 两者都过早停止，答案漏掉未展示的健康事件。 |
| L011 过去两周烘焙了几次 | 缺 | 缺失 | 缺失 | 两者都没有把食谱草稿误当实际烘焙，并提出补查关键词。 |
| P07 过去一个月参加几次聚餐 | 预审标注齐 | 缺失 | 缺失 | 两者找到三次，但因无法证明没有其他聚餐而继续怀疑；这也暴露计数题“证据齐”的标注与穷尽证明之间的张力。 |

四题均返回合格 JSON、真实原文连续引用，无 429 或格式错误。Luna 的实际推理与传输用时约 5–10 秒/题；测试为避免限流加入的等待使后三题端到端用时约 43–48 秒/题。这四题不足以比较两个模型的总体准确率，也不足以确认完整 257 题时不会再遇到限流。

## 事后核对与后续执行方式

P01 的新事实直接证明已读完，L011 没有把食谱草稿当实际烘焙，这两题符合预期。C037 明显不符合：首轮对话只有 Evan 一次明确的医院惊险经历，Sam 的体重/行动不适属于一般健康问题；原始材料另有 Sam 因胃炎急诊、Evan 心悸两次关键事件，模型未见到却判断“充分”。事后用“health scare Sam Evan”作为第二次 BM25 输入、排除已展示五段后，Top5 能找回这两段缺失原文。这只证明存在可行补查路径，不证明 Agent 会自主提出它。

P07 的预审标签认为三次聚餐的来源已齐，原参考答案是 `three`。两个模型都准确看到三次，但认为检索结果不能排除其他未展示聚餐。对精确总次数问题，这个怀疑有道理；“来源齐”不等于“已证明没有第四次”。此题应作为评估口径争议单列，不能简单算成模型误判或据它放宽提示词。上述事后核对不修改已冻结标签或首次模型输出。

用户随后纠正调用节奏：后续调用不再固定间隔；若遇 429，保存该次失败，等待 30 秒后对相同请求重试一次；再次 429 则停止。具体约定见 `execution-amendment-next-calls.json`。这项更改只对未来调用生效，不改写本次四题已经发生的 45 秒间隔和耗时。

运行：`python3 -B run.py`。程序只对未出现记录的固定题发起调用，已保存的首次输出不会被重跑覆盖。`records/*.json` 保留结果；`records/*.started.json` 保留请求开始记录。
