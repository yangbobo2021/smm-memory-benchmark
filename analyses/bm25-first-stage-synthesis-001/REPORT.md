# BM25 作为第一阶段检索底座：后续实验复盘

这是一份**技术路线判断**，不是上线可靠性证明：保留整段原始对话，用 BM25 快速给 Agent 返回候选，是当前最简单、可解释、可重放的第一阶段实现。不同 APP 可在它前后增加有来源约束的过滤和排序因素；对库存、日程、Bug 状态等需要确定性的业务事实，仍需相应业务数据与更新规则。BM25 的主要责任是找回原文，不能代替业务数据库、充分性判断或最终回答。

## “1000 段”的身份边界

P25/L32 的每题 1000 段保留其原题约 30–62 段来源，再加入 LongMemEval 其他题目的会话。`我`没有经过真实用户 ID 校验；不同题目的会话不能默认为同一人的连续记忆。C200 则把 272 段 LoCoMo 会话与 728 段 Conversation Chronicles 会话合并。它们同样不是一个人的自然历史。**这些是规模和干扰压力测试，不是单用户 1000 条记忆性能。**此前试验曾用数据集 `sample_id` 直接缩小检索范围；[原记录](../../experiments/smm-scoped-person-time-pilot-001/REPORT.md)已标记为不适用，不能拿那个成绩支持全库结论。

真实 APP 若在写入和查询时都由系统确定了用户／租户／权限边界，先按这一可信边界隔离数据是合理的工程条件；它不等同于在基准题中偷用研究者才知道的 `sample_id`。在身份边界内，仍可能出现同名、同主题、多个事件或时序版本，BM25 排序问题不会自动消失。

## 第一阶段实现与语义抽取的边界

1. **稳定底座**：原文和来源坐标保持不变；按已授权的用户／知识空间检索；对 Agent 给出的检索词执行整段 BM25，返回带有来源 ID、时间与匹配位置的候选。开放查看完整原文，便于 Agent 继续判断。当前实验只评价候选来源覆盖，尚不能保证最终答案。
2. **APP 已有的可信字段**：权限、真实用户 ID、业务对象 ID、数据类型、明确记录时间，可在相应场景用于范围限定或排序；范围条件若来源不可靠，应先核验，避免把正确来源过滤掉。尤其时间戳不等于事实发生时间。
3. **从原文推断的字段**：人物别名、本人发言与文档提及、事件类型、相对时间、项目归属等进入语义抽取。必须保留原句、提取来源和不确定性；可先用于增加检索入口或软加分，未经验证不要用作不可撤销的硬过滤。12题试验只验证了**字面姓名**，没有验证实体消歧或稳定人物 ID。
4. **领域状态**：厨房库存、日程安排、Bug 状态的当前值和更新需要独立的结构化规则与事实来源；BM25 继续提供原文证据和纠错入口。对一个领域的这些增强，不能推断其他 APP 也需要同一套结构。

目前证据支持“**先以 BM25 落地原文候选检索，再按 APP 的真实身份、权限、时间和业务对象逐步加入口**”这个实施顺序；不支持“仅凭 BM25 已达到可靠知识库”、固定 Top5 足够、关键词改写总能改善，或 12 题人物规则可普遍泛化。下一次验证若要评价真实个人助手，应使用同一真实或稳定模拟用户的持续事件流；如果评价多租户系统，需分别测试权限隔离与租户内排序。

离线复算：

```bash
python3 -B analyses/bm25-first-stage-synthesis-001/run.py --verify
```

不需要模型 API、向量服务或网络；`protocol.json` 锁定父输入 SHA。`results.json` 是本目录逐题数据，不覆盖任何前序实验首分。
